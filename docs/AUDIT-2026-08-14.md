# Usability, accessibility and localization audit

Run 2026-08-14 against the shipped build. Every finding below was **measured in a
real browser**, not inferred from reading the code. The probe scripts are in the
commit alongside this file.

Each issue carries three options and the one chosen, with the reason. Severity is
what it costs a real user, not how hard it is to fix.

---

## How the test was run

1. Cleared storage, loaded as a first-time user, walked the welcome flow.
2. Loaded the example data, then walked all five steps.
3. Ran DOM probes for focusable elements, accessible names, landmarks, heading
   order, live regions, dialog semantics, contrast ratios, and touch target
   sizes on each step.
4. Tested keyboard reachability with a modal open.
5. Tested browser Back, refresh and deep linking.
6. Counted the localization surface: user-visible strings, locale-sensitive
   formatting, and locale-specific logic in the parsing engine.

---

# Part 1. Usability

## U1. Browser Back exits the application entirely
**Severity: High.** Measured: on step 3, `location.href` is unchanged from load.
Pressing Back leaves the app. On a phone, Back is the primary navigation gesture,
so the most common way to say "go back one step" throws the user out of the tool.
Refresh always returns to step 1, and no step can be bookmarked or shared.

- **Option A.** Full client-side router (React Router). Real routes, real history.
  Rejected: a dependency and a rewrite of the shell for a five-panel wizard.
- **Option B.** Hash routing driven by the existing step state. `#evidence`,
  `#target`, `#match`, `#resume`, `#apply`. Back and Forward move between steps,
  refresh keeps your place, a step can be linked.
- **Option C.** Intercept Back with `history.pushState` and a `popstate` guard,
  keeping the URL clean. Rejected: it lies about where the user is and breaks
  refresh and sharing.

**Chosen: B.** No dependency, about forty lines, and it fixes Back, refresh,
bookmarking and sharing at once. The hash also survives the GitHub Pages
subpath, which a path router would need extra configuration to handle.

## U2. Destructive actions use native `confirm()`
**Severity: Low.** Three places call `confirm()`: deleting an entry, removing a
job, restoring a snapshot. It works and it is honest, but it is unstyled, it
cannot explain much, and on mobile it appears at the top of the screen far from
the thumb that pressed the button.

- **Option A.** Custom confirmation modal for all three. Correct, but adds a
  modal and more code to the destructive path.
- **Option B.** Undo instead of confirm: delete immediately, show "Entry deleted.
  Undo" in the toast for eight seconds. Fewer clicks in the common case.
- **Option C.** Leave as is.

**Chosen: C, for this pass.** Both A and B are improvements, but the confirm text
already names the entry being deleted, so nothing is lost silently, and the
accessibility issues below cost real users more. Logged rather than fixed.

## U3. "Open the application" is a dead control when a job has no URL
**Severity: Medium.** Measured on step 5: an `<a>` with no `href`, which is not
focusable, is not announced as a button, and looks identical to a live one apart
from opacity.

- **Option A.** Render a real `<button disabled>` when there is no URL.
- **Option B.** Hide it entirely when there is no URL.
- **Option C.** Keep the anchor and add `aria-disabled` plus `role="link"`.
  Rejected: still not focusable, still lies.

**Chosen: A.** A disabled button is focusable-by-default-off, announced
correctly, and explains itself with a title. Hiding it (B) makes the layout jump
between jobs.

# Part 2. Accessibility

## A1, A2, A3. Modals are not dialogs
**Severity: High. WCAG 2.4.3, 4.1.2.** Three separate measured defects in one
component:

- With the welcome modal open, **13 controls behind it are still tab-reachable**.
  Focus is not trapped.
- On open, `document.activeElement` is `BODY`. Focus is never moved into the
  dialog, so a screen reader user is not told anything happened.
- The container has no `role="dialog"`, no `aria-modal`, and no accessible name.

Note the deliberate product decision this must not undo: Escape and backdrop
clicks were removed on purpose, because people tab away to copy something, click
back, and lose what they typed. That decision is respected below.

- **Option A.** Native `<dialog>` element with `showModal()`. Gets the trap and
  the semantics free from the browser. Rejected: `showModal()` binds Escape to
  close with no supported way to prevent it in every browser, which breaks the
  product decision above.
- **Option B.** Add the semantics and a focus trap to the existing `Veil`
  component: `role="dialog"`, `aria-modal="true"`, an `aria-labelledby` pointing
  at each modal's heading, focus moved to the dialog on open, focus restored to
  the trigger on close, and a Tab handler that cycles within the dialog.
- **Option C.** Add `inert` to the background instead of a trap. Simpler, but
  `inert` support is uneven in older Safari, which is a real share of job
  seekers on phones.

**Chosen: B.** One component, every modal fixed at once, and the no-Escape
decision survives. Background also gets `aria-hidden` as a belt-and-braces
measure for screen readers that ignore focus containment.

## A4. Nothing is announced to a screen reader
**Severity: High. WCAG 4.1.3.** Measured: `[aria-live]` count is **zero** on every
step. That means the toast, form validation errors, search progress ("Reading
source 40 of 48"), and the AI status line are all invisible to a screen reader
user. On this product that is severe, because the toast is how the tool confirms
that an entry saved and how it reports what the importer changed.

- **Option A.** One global live region that everything routes through.
- **Option B.** Live regions per component: `role="status"` on the toast and
  progress lines, `role="alert"` on errors.
- **Option C.** Both: a global polite announcer for transient events, plus
  `role="alert"` on the inline validation messages that must interrupt.

**Chosen: C.** The toast and the progress line are genuinely global and transient,
so one announcer is right for them. A validation error sitting next to a field is
not transient and needs to interrupt, so it gets `alert` in place.

## A5, A6. No H1, no banner landmark
**Severity: Medium. WCAG 1.3.1.** Measured: headings start at H2 and there is no
`<header>` or `role="banner"`. A screen reader user navigating by heading has no
top-level anchor, and the product name is not in the heading structure at all.

- **Option A.** Make the product name in the top bar the H1.
- **Option B.** Make each step's title the H1, changing per step.
- **Option C.** Add a visually hidden H1 naming the current step.

**Chosen: B, with A as the landmark.** The step title is what the page is
actually about, and it changes as the user moves, which is what a heading should
do. The top bar becomes a `<header>` landmark carrying the brand, but not the H1.

## A7. Identity fields have no autocomplete
**Severity: Medium. WCAG 1.3.5.** Measured: all six heading fields carry
`autocomplete=MISSING`, and email and phone are `type="text"`, so a phone shows a
plain alphabetic keyboard for an email address.

- **Option A.** Add `autocomplete` tokens only.
- **Option B.** Add `autocomplete` plus the right `type` and `inputmode`.
- **Option C.** Leave off deliberately for privacy, so browsers do not store it.
  Rejected: the browser already stores everything this app does, locally, and
  refusing autofill costs a disabled user far more than it protects anyone.

**Chosen: B.** Both halves, on every identity field in the app, including the
answer bank where the same twelve questions are typed once and reused.

## A8. Repeated icon buttons are indistinguishable
**Severity: Medium. WCAG 4.1.2.** Measured on the evidence list: four buttons
named "Edit entry" and four named "Delete entry". A screen reader user hears the
same two names repeatedly with no way to tell which entry each belongs to.

- **Option A.** Name each button after its entry: "Edit entry: Northwind
  Logistics".
- **Option B.** Wrap each entry in a labelled group so the container provides the
  context.
- **Option C.** Add visually hidden text inside each button.

**Chosen: A.** Simplest, works in every screen reader, and reads correctly in a
list of buttons pulled out of context, which is exactly how they are browsed.

## A9. One colour contrast failure
**Severity: Medium. WCAG 1.4.3.** Measured: the "My estimate" badge, `#A0670F` on
`#FBF1DF`, is **4.22:1** against a 4.5:1 requirement. Every other pair on every
step passes.

- **Option A.** Darken the foreground token until it passes.
- **Option B.** Lighten the background token.
- **Option C.** Increase the badge font size to qualify as large text. Rejected:
  it fixes the ratio by lowering the bar, and the badge sits in a row of four
  that would then be inconsistent.

**Chosen: A.** `#A0670F` becomes `#8A5900`, which measures 5.4:1 on the same
background and is visually indistinguishable at badge size. The token is used in
five places and all of them improve.

## A10. Touch targets below the minimum
**Severity: Medium. WCAG 2.5.8.** Measured: the answer-bank copy buttons are
**12 x 28**, and the footer "Privacy and terms" link is **107 x 15**.

- **Option A.** Increase the rendered size of both.
- **Option B.** Keep the visual size and add invisible padding to reach 24 x 24.
- **Option C.** Leave, since 2.5.8 permits an exception when an equivalent control
  exists elsewhere. Rejected: for the copy button there is no equivalent.

**Chosen: A for the copy button** (it is an icon button and should match the
others at 28 x 28), **B for the footer link**, where growing the text would
unbalance the footer but vertical padding costs nothing.

## A11. No reduced-motion handling
**Severity: Low.** Measured: zero `prefers-reduced-motion` rules. There is a
spinning loader and a sliding toast.

- **Option A.** Media query that disables animation and transition globally.
- **Option B.** Replace the spinner with a static indicator for those users.
- **Option C.** Leave: the motion is small.

**Chosen: A.** Three lines, and it also covers any animation added later.

## A12. Validation errors are not associated with their fields
**Severity: Medium.** The entry form shows "Add the company or client." in a
message block, but nothing links it to the field it is about, and it is not
announced.

- **Option A.** `aria-describedby` from the field to the message, plus
  `aria-invalid` on the failing field.
- **Option B.** Move focus to the first failing field on submit.
- **Option C.** Both.

**Chosen: C.** Association makes it correct; moving focus makes it useful, and it
helps sighted keyboard users just as much.

# Part 3. Localization

## L1, L2, L6. There is no localization layer at all
**Severity: High, given the goal.** Measured: roughly **590 user-visible strings**
hardcoded across 18 components, `lang` hardcoded to `en`, no `dir` attribute, no
way to choose a language, and no detection of the browser's preference.

- **Option A.** Add `react-i18next`. Industry standard, plurals, interpolation,
  lazy loading. Rejected here: a runtime dependency and a config surface for a
  static app whose whole pitch is that it has no moving parts, and it would be
  the app's first non-React dependency.
- **Option B.** A small typed catalogue. One `strings` object per locale, a
  `useT()` hook, `Intl` for everything numeric and temporal, `lang` and `dir`
  driven from the active locale, a picker in the top bar, and
  `navigator.languages` detection on first run. Missing keys become **compile
  errors**, because each locale is typed against the English catalogue.
- **Option C.** Ship English only and document that translation is out of scope.

**Chosen: B.** It gives every practical benefit of A at a fraction of the weight,
and the typing is a genuine advantage over `react-i18next`: a translator cannot
forget a key, because the build fails.

## L3. Formatting is partly locale-aware and partly not
**Severity: Medium.** Dates and counts already use `toLocaleDateString` and
`toLocaleString` with no explicit locale, so they follow the browser correctly.
Pay formatting does not: it hardcodes `k`, `/hr`, `/day`, `/mo` and only
recognises the symbols `$`, `£` and `€`.

- **Option A.** `Intl.NumberFormat` with currency style throughout.
- **Option B.** `Intl.NumberFormat` with `notation: "compact"` for the abbreviated
  form, and translated period suffixes.
- **Option C.** Leave, since pay comes from the posting.

**Chosen: B.** Compact notation is what `140k` is trying to be, and `Intl`
produces the right abbreviation per language. The currency symbols stay as
detected, because they are read out of the posting rather than chosen by the app.

## L4. The resume parser is English-only
**Severity: Medium, and only partly fixable.** The importer recognises English
month names, English section headings such as EXPERIENCE and SKILLS, an English
stop-word list, and English metric words. A French or German resume will import
badly.

- **Option A.** Per-locale parser dictionaries: month names, section headings and
  stop words per language.
- **Option B.** Ship the English parser, detect when a resume does not look
  English, and tell the user plainly, pointing them at the clean-up prompt that
  already exists and works in any language because their own AI does the work.
- **Option C.** Claim nothing and let it fail quietly.

**Chosen: B for this pass, with A as the documented next step.** Doing A properly
means sourcing real section-heading conventions per country rather than
translating the English ones, which is research this pass cannot do honestly. B
is truthful and already has a working escape hatch. The detection and the message
are implemented; the dictionaries are scaffolded so a language can be added
without touching the parser.

## L5. Geography covers twelve countries
**Severity: Low to Medium.** Twelve countries with English names only, so a user
typing "Deutschland" or "España" gets nothing.

- **Option A.** Full country dataset. Rejected: a large dependency for a feature
  whose job boards are overwhelmingly English-language anyway.
- **Option B.** Add native-language names and demonyms as aliases to the twelve
  existing entries, which is where the actual failure is.
- **Option C.** Leave.

**Chosen: B.** Small, targeted, and it fixes the case that actually breaks.

# Part 4. What was executed, and the re-test that proves it

Every chosen option above was implemented, and every one was **re-measured in
the browser after the fix**, not assumed. Before and after, from the probes:

| Finding | Before (measured) | After (measured) |
|---|---|---|
| U1 Back exits the app | Back → `about:blank`, refresh → step 1 | Hash routing: `history.back()` moved `#resume` → `#match` and the UI followed; refresh keeps the step; steps are linkable |
| U3 dead anchor | `<a>` with no href, not focusable | Real `<button disabled>` with a title explaining why |
| A1 focus trap | 13 controls behind the modal reachable | Tab from the last control wraps to the first, `defaultPrevented=true` |
| A2 focus on open | `activeElement` = `BODY` | `activeElement` = the dialog's first button |
| A3 dialog semantics | no role, no `aria-modal`, no name | `role="dialog"`, `aria-modal="true"`, named per modal; background siblings `aria-hidden` (4 of 4), dialog itself not hidden |
| A4 live regions | 0 on every step | Toast is `role="status"`; error messages are `role="alert"`; verified announced text present |
| A5/A6 heading and landmark | no H1, no header | Each step's title is the H1 (5 of 5 verified); top bar is a `<header>`; skip link added |
| A7 autocomplete | all six identity fields `MISSING`, email/phone as `type=text` | `name`, `organization-title`, `address-level2`, `email`, `tel`, `url`, with matching `type` and `inputmode` |
| A8 duplicate names | 4x "Edit entry", 4x "Delete entry" | Named by employer plus the opening words of the entry |
| A9 contrast | 4.22:1 on the estimate badge | Token darkened to `#8A5900`; probe reports zero failures |
| A10 target size | copy button 12x28, footer link 107x15 | Probe reports zero controls under 24x24 |
| A11 reduced motion | 0 rules | Global `prefers-reduced-motion` block, and the step scroll checks the preference too |
| A12 error association | message unlinked, nothing focused | `role="alert"`, `aria-invalid` on the field, `aria-describedby` to the message, focus moved to the failing field; verified end to end |
| L1/L2/L6 no i18n | ~590 hardcoded strings, `lang` fixed, no picker | Typed catalogue with English and Spanish, picker in the top bar, browser-preference detection, choice persisted, `lang`/`dir` driven from the locale; verified: switching renders "Todo lo que has hecho…" and survives reload |
| L3 pay formatting | hardcoded `k`, `/hr` | `Intl.NumberFormat` compact notation, translated period suffixes |
| L4 English-only parser | fails silently on other languages | Detector for es/fr/de/pt/it/nl markers; verified: a French resume triggers the warning and routes to the clean-up prompt |
| L5 geography | English names only | Native names and demonyms on all twelve countries |
| New: 3px overflow at 320px | answer row pushed the page wide after the button fix | select's `flex:none` + inline width removed; 320/320 on every step |

**A bug found in my own fix, worth recording.** The first version of the
background `aria-hidden` targeted `document.body.children`. The whole app,
modal included, renders inside one root element, so that would have hidden the
dialog along with the page. The re-probe caught it; the fix targets the veil's
siblings inside the root. The lesson is the same one this project keeps
teaching: measure the fix with the same instrument that found the defect.

**Honest limits of this pass, so nobody reads more into it than it is:**

- The i18n catalogue covers the shell, the welcome flow and the whole Evidence
  step. The Target, Match, Resume and Apply panels and the advanced modals still
  render English strings; the catalogue and provider are in place, so finishing
  them is translation work, not engineering work. Spanish is the one shipped
  translation and it was written in-session, not reviewed by a native speaker.
- RTL is styled and the `dir` attribute switches with the locale, but no RTL
  language ships yet, so it is verified only by inspection.
- The resume parser itself still reads English. The fix shipped is honest
  detection plus a working escape hatch, not a multilingual parser. Per-locale
  dictionaries are the documented next step.
- The `confirm()` dialogs (U2) were logged and deliberately left.
- WCAG conformance is not claimed. The audit covered the essentials it names,
  with probes committed alongside; it is not a certified assessment.
